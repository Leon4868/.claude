## 一、先把"嵌"的四种含义拆开，别混着谈

我认为讨论之前必须先分清，否则各说各的：

- **嵌法 A —— 当通用 Agent 运行时**：直接用 harness 承载 PRD 8.2 定义的 Agent 运行时（读已发布配置，执行 RAG、模型推理、工具调用、人工审批，带步数/Token/工具调用/超时上限）。平台不自研编排内核。
- **嵌法 B —— 当 Tool 层的沙箱执行器**：harness 不是运行时，而是被 Tool 中心注册的一个工具/执行后端，专门承接"需要在沙箱里跑代码、做数据分析、批处理文件"的任务。它在模型网关下游，受风险分级和审批策略管辖。
- **嵌法 C —— 当参考实现**：不嵌代码，只借鉴它的设计（沙箱分级、审批模式、事件流、rollout 日志结构、工具调用协议）来自研。
- **嵌法 D —— 不进产品，只做研发内部工具**：明确排除在产品之外。

请你的回答始终标明在讨论哪一种，不要笼统说"可以/不可以嵌"。

## 二、我的判断

**嵌法 A 不成立。嵌法 B 有条件成立但本期无位置。嵌法 C 是当前最有价值的。**

### 反对嵌法 A 的理由，我认为有三条是结构性的（改不动）

**1. 工具面根本不匹配。** Codex harness 的核心工具面是 shell + 文件读写 + patch。企业中台 Agent 要的是 OA / CRM / ERP / 工单 / 订单这类**受控 HTTP 工具**，PRD 7.5 要求每个工具有输入输出 Schema、风险分级（只读 / 低风险写 / 高风险写）、认证、幂等、限流、错误映射。用一个以 shell 为中心的 harness 承载它们，等于把"任意命令执行"引进企业系统——而 PRD 产品原则第 4 条明写"只读优先、写入受控"，shell 恰恰是最不受控的写入面。

**2. 权限模型不在同一维度。** PRD 要求权限前置（检索前过滤）、RBAC + ABAC、每次调用可追溯到具体用户和数据归属。Codex 的权限模型是**进程级沙箱 + 目录白名单 + 审批模式**，回答的是"这个进程能碰哪些文件、能不能联网"，不是"这个用户能看哪条数据"。嵌套后企业侧的用户级数据权限无法下沉进 harness——harness 内部每一步都是同一个进程身份。

**3. 多租户模型不兼容。** Codex harness 是单用户单工作区模型；中台要的是多用户并发 + 部门隔离 + 每用户额度。

### 另外两条我原本想列为冲突，但自己检查后认为**是可解的，不该算结构性障碍**

**4. 成本绕过模型网关** —— 我原本认为这直接违背 PRD 的立项动机（成本不可见）。但 Codex 支持自定义 model provider 的 base_url，理论上可以指向企业自己的 OpenAI 兼容网关，让调用重新落回 `usage_ledger`。所以这是**配置和适配工作量问题，不是架构不可能**。

**5. 审计粒度对不上** —— 我原本认为 harness 内部步骤无法对齐企业 trace 体系。但它有 JSONL 事件流和 rollout 日志可导出，做一层映射到企业 traceId 是可行的。同样是**工作量问题**。

我把这两条从"结构性冲突"里撤回。如果你认为撤早了、它们其实仍然是硬障碍，请说明为什么。
